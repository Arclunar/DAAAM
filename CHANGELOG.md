# Changelog

All notable changes to this project are documented in this file.

## 2026-10-17

### Added

- Added contextual scene questions to the replay workspace. Every result tab has a `问答` page next to `实体` and `任务` whose conversation belongs to that result alone: the service keeps it in `.replay-web/history/`, so a reload, a second window or a restart shows it again, and no other result ever sees it. `GET /api/runs/{id}/chat` returns the conversation, whether a question is being answered, whether the active scene graph can answer (`ready`, `reason`, `graph`) and the allowlisted models with whether each has an API key (never the key); `POST` takes `{question, model, include_view_context, view_context}` and streams the answer as server-sent events (`turn`, `progress`, `delta`, then `complete` or `error`); `DELETE` clears that one conversation. Mutations need the page's origin and the CSRF token. Before anything is stored a question is refused with 400 (unknown field or model, empty or longer than 4,000 characters), 503 `no-credentials` (no key for the model in the environment or `.env`; only its presence is read and it stays with the service and worker), 409 `busy` (another question of the result is still being answered) or 409 `not-ready` (the graph has no sentence embeddings: run Postprocess first). A question then runs in a fixed order: the result's active validated scene graph is captured once and staged for the worker by digest, so a hot reload during the turn only affects later turns; the earlier conversation is bounded (whole answered turns only, at most 56,000 bytes; boundary rows, error rows and unanswered questions never reach the model); a boundary row is stored when the graph version differs from the one the conversation last used; the question is stored; the answer streams; and only its text is stored as the assistant message, before it is announced, or, on a failure, a retryable error row with a fixed message (never an exception's text, a prompt, tool arguments or results, or model reasoning). If the page goes away the worker still finishes and the answer is there at the next look. The current view (replay time, 3D camera and the selected entity, which the service describes from the scene graph by its id, never from the request) goes along only while `包含当前视图上下文` is checked. The panel has the model selector (models without a key are disabled and say so), the conversation rendered as text, the Agent's progress as `第 N 轮`, `查询场景: <tool>` or its place in the queue, Ctrl+Enter to send, `停止显示` (stop waiting; the answer shows up in the conversation later), `清空对话` after a confirmation, the model and the scene graph file with its short version on every answer, a notice when the graph was replaced since the last answer, the reason when it cannot ask (`请先运行 postprocess`, a missing key, no scene graph) and `重试` on failures. Questions can be asked while a processing job runs, against the last valid graph, and a background tab's panel stays current from `chat` events. `--agent-models`, `--no-agent` and `--agent-idle-seconds` of `scripts/replay_web/server.py` set the allowlist, switch the panel off and tune the worker's idle exit. Covered by 74 service tests with a fake worker (validation, order of storage, graph capture during a hot reload, provenance, retry, clearing, isolation between results, keys never leaving the service, nothing private in the stored history) and by real-browser tests of a question and its follow-up, a reload, two results, a new graph version, the view toggle, an unready graph, a question left unwatched, failures, refusals and asking during a job.
- Added the shared Agent worker of the replay chat. `scripts/replay_web/agent_worker.py` is one long-lived process in the `daaam-ws` container (`docker compose run --rm -T --name daaam-replay-agent ... python -m scripts.replay_web.agent_worker`) that answers scene questions for every tab and result over a validated NDJSON protocol (`agent_protocol.py`: `inspect`, `ask` and `invalidate` requests; `progress`, `delta`, `complete` and `error` events), keeping the models and loaded graphs in the Agent cache. It reads only graph snapshots staged under `.replay-web/cache/`, keeps standard output (down to the C level) free of everything but protocol events, sends only the answer text, iteration numbers and tool names (never prompts, tool arguments or results, model reasoning or API keys), masks keys in its log, reports failures with fixed messages, and ends after 15 idle minutes (`REPLAY_AGENT_IDLE_SECONDS`) or at end of input so the GPU is free again. The models a question may name are the `REPLAY_AGENT_MODELS` allowlist (default `gpt-5-mini`). `agent_client.py` is the service side: a first-in-first-out queue in front of the single process, one automatic restart when the worker dies before streaming any of an answer, timeouts that stop a silent worker, release when idle, an orderly stop that closes the worker's input before stopping the fixed container by name, and atomic, digest-checked staging of graph snapshots with bounded retention.
- Added persistent chat history for the replay workspace (`scripts/replay_web/history.py`, standard library only). Each result has its own conversation under `.replay-web/history/<sha256 of its canonical path>/`: `messages.jsonl` appends one flushed line per question, answer, graph-change boundary or error, recording the model, the graph file and its version and the replay view a question was asked in, and `meta.json` holds the schema version, the canonical path and creation time. Different spellings of one path share a history, other results never see it, a half-written or malformed line is moved to `quarantine.jsonl` without losing the earlier turns, and clearing renames the exact directory to a trash sibling before deleting it (never following a link out of the root). `context_messages()` gives a model the newest whole turns within 32,000 characters plus one deterministic extractive summary line (at most 400 characters, with the graph the answer came from) per older exchange, in all at most 48,000 characters and 60,000 bytes, and without any provider call; boundary and error rows are never sent.
- Added the query setup of the replay chat (`scripts/replay_web/query.py`, standard library only until a graph is loaded). `DatasetContext.from_manifest` takes the dataset kind, sequence and time origin from the validated manifest, never from a folder name. `load_query_graph` loads a graph the way the scene tools expect it: TUM keeps its run-relative timestamps, CODa is shifted by the manifest's time origin and enriched from an optional `background_objects.yaml`, and objects without a description are dropped for both. `query_capability` reads a graph file and says whether it can answer questions (sentence-embedding provenance and embedded objects, otherwise "run Postprocess first"). `AgentCache` keeps one loaded graph version per result (two results at most, least recently used out), one Agent per model over it and the CLIP/sentence encoders shared, so a graph change affects only later questions and the heavy models are never built per question or tab.
- Added conversation context and progress events to the scene understanding Agent: `SceneUnderstandingAgent.answer_query(..., conversation=, context=, progress=)`. Earlier turns (`{"role": "user"|"assistant", "content": str}`, oldest first) reach OpenAI as plain messages ahead of the question and Anthropic as merged text turns that start with a user turn; `context` renders only `replay_time`, `camera` and `selected_entity`, one line each, in front of the question; the final structured call keeps the whole conversation; invalid turns or more than 64 KiB of conversation and context raise `ValueError` before any provider call. `progress` receives only `{"type": "iteration", "number", "maximum"}`, `{"type": "tool", "name"}` and `{"type": "final"}` (never prompts, tool arguments or results, or reasoning), and a callback that raises is logged without failing the query. Calls without the new keywords send the same requests and return the same `(response, history, messages)` as before.
- Added post-processing from the replay page. `POST /api/runs/{id}/jobs` starts one stage (`{"stage": "postprocess" | "summarize" | "all", "replace": false}`, answered `201` with the job), `GET /api/runs/{id}/jobs` returns the newest jobs, the output of the running and of the newest one and what each stage may do right now (available, needs confirmation, or why not: conflict, prerequisite, api-key), and `POST /api/jobs/{id}/cancel` stops one. They need the page's origin and the CSRF token, reject unknown stages and fields with 400, and refuse with codes and statuses (`confirm`, `busy` 409; `prerequisite`, `api-key` 422; `conflict`, `state` 409); the dataset kind and path of the command come from the opened result, never from the request. Each result tab gets a `任务` page in its sidebar with `Postprocess`, `Summarize`, `全部运行` and `取消`: the buttons follow what the service says (Summarize stays disabled with its reason until `clustered_dsg.json` exists and an API key is configured, and every stage waits while the result has a job), a stage over existing outputs shows `重新运行 …` and an inline confirmation naming the files it will replace, recent jobs show their state, exit status and a `重试` button when they failed, and the latest job's output streams into a 500-line log. A job's end refreshes the stage state at once; a successful job's new graph appears through the graph hot reload, while a failed or cancelled job never changes the shown graph. A background tab keeps its jobs and log current from the events and shows only its small marker (running, finished, failed) until it is shown. Covered by API tests with a fake process runner and by real-browser tests of streaming and promotion, confirmation, cancelling, failure and retry, the missing key and a background tab.
- Added supervised processing jobs for the replay workspace (`scripts/replay_web/jobs.py`; the browser routes follow separately). A job is Postprocess, Summarize or Run all on one open result and runs as the fixed command `docker compose run --rm -T --name daaam-replay-job-<id> -v <result>:/selected-result [-e settings] daaam-ws bash scripts/postprocess_coda.sh --atomic --stage <stage> /selected-result`, executed without a shell (TUM results add their place layer and clustering config, CODa uses the script's defaults; the dataset kind comes from the bundle's manifest, never the folder name). The manager allows one unfinished job per result and `--max-jobs` running jobs in total (default 1, the others wait in order), refuses Summarize without `clustered_dsg.json` or without an `OPENAI_API_KEY` (found in the environment or `.env`; only its presence is read), asks for confirmation (`replace`) before running a stage over its existing outputs, and does not start while another DAAAM pipeline, depth estimate, post-processing or query container is running (the rule of the justfile's `_coda-guard`). A job counts as succeeded only if the child exited 0 and its outputs were written during the run. Cancelling asks the job's process group to stop, after ten seconds stops its own container by name, and finally kills the group. Each job is a record plus a log cut to its last 256 KB under `.replay-web/jobs/<id>/`; progress is published as `job-state` and batched `job-log` events on the result's stream and included in every new stream's `state`. After a service restart, jobs that were queued or running become `interrupted` (their containers are stopped) and a result's history follows its path to its new run ID; a successful job makes the service rescan the result's scene graphs at once. Covered by `tests/test_replay_jobs.py` with a fake process runner (no Docker) and by service wiring tests.
- Added stage selection and atomic publication to the post-processing script. `scripts/postprocess_coda.sh --stage postprocess|summarize|all` runs the embeddings and place clustering, only the OpenAI region summaries (which refuse a result without `clustered_dsg.json`), or both one after the other; `--summaries` stays the spelling of `--stage all`, no stage means postprocess, and an unknown stage or `--summaries` with another stage exits 2. With `--atomic` every step writes next to its final file under a `.replay-job-<pid>-` name (the clustering gets explicit `src_dsg:=`/`save_dsg:=` paths, also through the `PLACES` adapter), and each stage publishes its files together by rename after copying the old ones aside, putting them back if a rename fails; a failing step, Ctrl+C or termination (exit 130/143) leaves `dsg_updated.json`, `clustered_dsg.json`, `clustered_dsg_with_summaries.json` and `region_summaries.yaml` byte-identical and removes only that process's own temporary files. `postprocess_scene_graph.py --output` and `summarize_regions.py --summary-output/--scene-graph-output` name the files explicitly (the defaults are unchanged), and `region_summaries.yaml` is now written through a temporary file and renamed in every mode. Without `--atomic` the steps are called exactly as before, so `coda-post`, `coda-summarize`, `tum-post` and `tum-summarize` behave as they did; the replay workspace's processing jobs will use `--atomic`. Checked in the `daaam-ws` container on a copy of a real TUM result: both stages ran through a bind mount at `/selected-result`, published their files without leftovers, and the embedded and clustered graphs are byte-identical to the ones the old script wrote.
- Added live scene graph updates to the replay workspace. The service follows the graph files of every open result (`ArtifactMonitor`, started and stopped with the server; `--graph-interval` sets the two-second poll) and publishes `graph` (initial, activated, promoted, demoted, updated, removed, none), `artifact-error` and `state` events through server-sent events (`scripts/replay_web/events.py`): a bounded per-result history with event ids that carry a random per-start epoch lets a reconnecting page resume from `Last-Event-ID`, and a page that cannot resume (history gap, an id from another service start, or a reader too slow to keep up) gets one current-state event instead; idle streams send heartbeat comments, a closed connection releases its subscription and stopping the server ends every stream. New routes: `GET /api/runs/{id}/graph` (active version with file name, digest, size, time and rank, the state of every candidate file, and a compact document of objects, places and rooms with their summaries — no meshes, feature vectors, embeddings, model reasoning or host paths), `GET /api/runs/{id}/events` for one result and `GET /api/events?run=…` for several over one connection, because a browser allows only a handful of connections per origin. In the page every tab follows its result through that one shared stream: the active tab applies a new graph without moving time, the 3D camera, visibility or the camera cards, and shows its file name, version and counts beside the dataset badge with one notice per version; a background tab shows a marker and applies the newest version when it is shown. The selection stays unless the previous graph contained the selected entity and the new one does not, in which case it is cleared with a visible reason. The entity browser gains a read-only `房间` tab with room labels, summaries and counts, and object and place details name their place and room in the graph. A bad higher-priority file is reported once and the valid graph stays. When the service restarts or another page closes a result, its tab opens the path again and keeps its view, and a mutation refused for a stale CSRF token is retried once with a fresh one. Covered by `tests/test_replay_events.py`, the server tests and real-browser hot-reload tests in Windows Chrome.
- Added scene graph selection and change monitoring for open replay results (`scripts/replay_web/artifacts.py`). A result's active graph is the most processed valid file in the fixed order `clustered_dsg_with_summaries.json`, `clustered_dsg.json`, `dsg_updated.json`, `dsg.json`; a file counts only when it is complete UTF-8 JSON with a well-formed node and edge list, stays inside the result directory and is under 512 MiB. A later partial or broken rewrite of the active file keeps its last valid version, and an invalid candidate is reported once per bad version (a file this fresh is first given a poll to finish being written). `ArtifactMonitor` checks every open result every two seconds by comparing size, times and inode, reads a file again only when it changed, detects same-size rewrites by SHA-256 digest, parses one graph at a time (the 99 MB CODa graph takes about 2 s and 0.7 GB peak) and keeps only a compact summary of the active graph — objects, places, rooms with their summaries, node counts and embedding model names, without meshes, feature vectors or model reasoning. It reports `graph` (initial, activated, promoted, demoted, updated, removed, none) and `artifact-error` changes through one callback, and one failing result or listener does not stop the others. The run registry now announces opened and closed results to listeners so a newly opened result is scanned at once. Checked against the real TUM `fr1_desk2` and CODa results; `tests/test_replay_artifacts.py` covers priority, fallback, promotion, demotion, removal, same-size rewrites, partial writes, isolation between results and the monitor thread.
- Added movable camera cards to the replay viewer: the current-time RGB and depth images are dragged by their title bar (or moved with the arrow keys while it has focus, Shift for 1 px), come to the front when clicked, stay inside the viewer when the window shrinks, and keep their positions, stacking order and enlarged size per result tab across reloads; `重置相机布局` puts them back next to the sidebar. Moving a card never moves the timeline or the 3D view.
- Added multi-result tabs to the replay workspace: results open from the `output/` list or any typed path into isolated, labelled tabs (`TUM / fr1_desk`, `CODa / 0`); opening an open result again focuses its tab, tabs reorder by dragging, Left/Right/Home/End move between them and Delete closes one (closing releases the service's run ID only; no file is deleted). Open paths, their order, the active tab and per-tab viewer state are restored after a reload from local storage (never service run IDs); a saved path that no longer opens is skipped with a notice while the others reopen. Only the active pane is visible, and panes are told before they are shown or hidden. Real-browser tests drive Windows Chrome (as `just test` does) against a fixture service that `wsl.exe` starts inside WSL, where it finalizes real bundles and serves the workspace (`tests/replay_web_fixture_server.py`).
- Added `just replay-web [host] [port]` and the repository's single root `replay.html`. A standard-library loopback service on the WSL host (`python3 -m scripts.replay_web.server`, Python 3.8) serves the page, its static files and an API for the result list, opening a result by path (returning an opaque run ID) and only the members an open bundle's manifest names (gzip timeline chunks, images, the reference mesh) with ETags and immutable caching keyed by bundle version. It binds 127.0.0.1/localhost only, refuses foreign Host headers (DNS rebinding), requires the page origin plus a startup CSRF token for POST/DELETE, limits JSON bodies to 64 KiB, sends a strict Content-Security-Policy and has no general file-read endpoint. Its local state directory `.replay-web/` is ignored by git.
- Added result paths for the replay workspace (`scripts/replay_web/paths.py`, `runs.py`): `/home/...`, `/mnt/<drive>/...`, `C:\...` (also with `/` and Explorer's surrounding quotes) and `\\wsl.localhost\<distro>\...` / `\\wsl$\...` paths of the current distribution become Linux paths; other distributions, network shares and relative paths are rejected. An opened result is registered under its canonical path (symlinks and `.`/`..` resolved, the bundle directory or manifest also accepted) behind a random opaque run ID that stays stable while it is open and is never reused, and discovery lists valid bundles below `output/` newest first with a bounded, loop-safe walk that follows the `output/coda` symlink without opening anything.
- Added `python scripts/replay.py finalize`, which turns a replay recording — or, for a run without one such as CODa, its final `dsg.json` as a single snapshot — into the run's `replay/` data bundle: gzip JSON timeline chunks bounded by snapshot count and uncompressed size, RGB and colour-depth images per snapshot, the exact DAM description-source frames, an optional separate reference-mesh member, and `manifest.json` written last. The bundle is built beside the target, validated with digests and published by directory rename, so a previous valid bundle survives any failure. TUM and CODa layouts are selected by an explicit dataset kind (`scripts/replay_datasets.py`): CODa frames are ordered by number, its time origin is the first line of `timestamps/<seq>.txt`, and run frame IDs are offset by the start frame and checked against the recorded image stamp, so a description frame is never guessed. The retained 250-snapshot `fr3_long_office_household` recording finalizes in 21 s into 17 chunks of at most 8.3 MB.
- Added the versioned replay bundle contract (`scripts/replay_web/manifest.py`, schema 1). A mapping result is openable in the replay workspace only when its `replay/manifest.json` is finalized and valid: required keys and types are checked without silent defaults, chunks must cover the snapshots in order with matching sizes (digests on request), and every chunk, image and reference member must be a normalized relative path that stays inside the bundle after following symlinks. JSON state is written through a temporary sibling and an atomic rename. `tests/test_replay_manifest.py` covers the schema and the path-traversal boundary.
- Added `TODO_UNIFIED_REPLAY_WORKSPACE.md`, a complete AI handoff for the approved single-entry replay workspace. It records the current implementation status, authoritative design and plan commits, settled TUM/CODa bundle and service contracts, hot-reload/job/Agent safety boundaries, phased checklist, verification expectations and the supersession of per-result HTML assumptions.

### Changed

Starting a processing job makes an idle Agent worker leave the GPU, closing a result lets the worker drop its cached graph (the conversation stays on disk) and stopping the service stops the worker.
- `scripts/demo_query.py` now also queries TUM graphs: `--dataset-kind tum|coda`, `--time-origin` and `--sequence` were added and `--seq-id` alone still means a CODa sequence. It loads the graph and picks the four read-only tools through the same helpers as the replay chat, and `preprocess_scene_graph` no longer warns about a start time of 0 (a run that is already relative).
- `USAGE.md` 9.0.1 now explains the scene graph hot reload (the fixed four-file order, the two-second poll and `--graph-interval`, what counts as a valid file, how a bad file or a deleted one is handled, what stays put when a version changes, the new 房间 list) and a new 9.0.2 explains processing from the page: what Postprocess, Summarize and 全部运行 do and need, the fixed container command and the one result directory it mounts, confirmation before replacing outputs, one job per result and `--max-jobs`, the live 500-line log, cancelling (the container is stopped by name and the job ends when it is gone), what a restart does to unfinished jobs and where the records live (`.replay-web/jobs/`), and the unchanged command-line recipes with the new `--stage` and `--atomic`. Measured on this machine through the service: a 30-frame TUM result Postprocess 16–21 s, Summarize 3 s; the 60-frame CODa result Postprocess 18 s; a CODa result with 208 objects Postprocess 34 s and Summarize 36 s with two real OpenAI calls (rooms `urban sidewalk` and `city sidewalk` appeared in the page). `DOCKER.md` describes the `daaam-replay-job-<id>` containers and how to inspect and stop them after a hard kill. `just test` now also runs the artifact, event and job suites on the host, and the recipe comment mentions page processing. The state sent to a page now carries up to 500 log lines (about 100,000 characters) of a result's latest job instead of 100, so the page keeps the whole output after the job ends.
- `USAGE.md` 9.0.1 now documents the replay workspace instead of opening generated pages: `just tum-run` → `just replay-web` → open the result tab, the `replay/` bundle layout and its manifest, accepted Linux/Windows/WSL path forms, multi-result tabs, camera-card layout and reset, the service boundary, no compatibility with old self-contained pages, optional `replay.rrd`, and recovery from a retained `.replay-recording` with `python scripts/replay.py finalize`. Section 4.4 explains the CODa bag sidecar, the one-snapshot CODa bundle and how to give an older CODa result a bundle; sections 7, 9.5 and 9.6 and the test overview describe bundles instead of pages, and `DOCKER.md` explains why the service runs on the WSL host. `just test` runs the new host suites (manifest, datasets, paths, run registry, HTTP service), the bundle suite in the container and both real-browser modules. Verified end to end on this machine: `just tum-test 30 fr1_desk` produced `output/tum_rrd_test/out_20261016_183910/replay/` (8 snapshots, reference mesh) and no HTML; a fresh 60-frame CODa bag from frame 821 (`just coda-bag 821 60`, then `just coda-run`) produced the one-snapshot bundle of `output/coda/out_20261016_184313` whose dataset kind, sequence, start frame, frame count, frame rate and time origin match the bag's sidecar; both opened side by side as tabs in `just replay-web`, and a real CODa description-source frame opened without moving time. `TODO_UNIFIED_REPLAY_WORKSPACE.md` marks Phase 1 complete.
- The replay viewer now lives in the workspace (`scripts/replay_web/static/viewer.js`, `replay_data.js`): every result tab owns a WebGL viewer that loads gzip timeline chunks over HTTP through bounded caches (three chunks, twelve decoded snapshots), prefetches only the neighbouring chunks of the active tab, loads camera and description-source images by URL and the reference mesh once, and renders, plays and decodes images only while its tab is active (playback pauses in the background and resumes on return). Mesh source switching, stable label modes, the amber selection overlay, picking, the entity browser and timestamp playback behave as before. Selecting an Object or Place and the `描述源帧` modal never move the timeline; an object without recorded provenance shows a disabled `无描述源帧`; a corrupt chunk stops only that result and names the chunk; each tab's time, camera, controls, selection and hidden entities come back after a reload.
- New mapping results no longer contain a generated `replay.html`. `scripts/run_replay.sh` (`just tum-run`, `just tum-test`) finalizes `RUN/replay/` with the explicit dataset kind `tum` and the run's sequence and prints the result directory and `just replay-web` instead of a file path; `just tum-run` reports only a result created by its own invocation. Old self-contained pages are intentionally not supported by the new workspace.
- `scripts/make_coda_bag.sh` (`just coda-bag`) checks the requested frame range against `timestamps/0.txt` before recording and, once the bag is closed, atomically writes `daaam_replay.json` into it (dataset kind, sequence, first frame, frame count, 10 Hz, time origin). `scripts/run_coda_example.sh` (`just coda-run`) finalizes a one-snapshot replay bundle from the final `dsg.json` of the result created by its own run, using that sidecar rather than the bag name; a bag without the sidecar keeps its mapping result but exits with status 3 and prints the `just coda-bag` command that records a supported bag. `scripts/run_coda_chunks.sh` reuses only bags that carry the sidecar and records older ones again.

### Fixed

- Cancelling a processing job from the replay page now really stops it. Tried against Docker, ending the `docker compose run` client made it exit within seconds while its container kept running: the job was reported cancelled and then published its outputs anyway. The job manager now stops the job's container by name (`docker stop`, asked again while the container may not exist yet, and only if that does not work within ten seconds the client is signalled and finally killed), keeps a job running until its container is gone — also when the client ended on its own — and from the host removes the temporaries a killed container left next to the outputs and rolls back a publish it was in the middle of. `scripts/postprocess_coda.sh` now runs its steps so that a SIGTERM to the script alone (what `docker stop` sends) stops the step at once and still removes its temporary files, and jobs set `PYTHONUNBUFFERED=1` so the log shows the output as it happens. Checked on a real TUM result: three seconds after the cancel request the container was gone, nothing was left behind and the outputs were byte-identical.

### Removed

- Removed the per-result page builder: `python scripts/replay.py build`, its template `scripts/replay_viewer.html` and the page-only image helpers. Recordings are finalized with `replay.py finalize` and viewed with `just replay-web`.

## 2026-10-16

### Added

- Added three TDD implementation plans for the unified replay workspace: the central replay bundle/service and multi-result viewer, hot scene-graph updates with safe web-launched processing jobs, and persistent version-attributed multi-turn Agent conversations. Each phase defines exact interfaces, tests, verification commands, migration boundaries, and reviewable commits.
- Added the approved architecture for a single workspace-level `replay.html` backed by a loopback WSL service and versioned per-result replay bundles. The design supports TUM and CODa, several isolated result tabs, arbitrary WSL-visible paths, chunked playback, movable camera cards, exact object description frames without timeline jumps, hot scene-graph promotion, web-triggered post-processing/summarization, and persistent contextual Agent chat without per-output HTML files.
- Added exact DAM description provenance for every newly described object: the selected pipeline frame ID and timestamp now survive multi-image grounding and are stored separately from the object's full observation history in `corrections.yaml`. Replay builds read those RGB frames from the dataset offline; every object row has a source-frame button that opens the exact image without moving the timeline, while ordinary map/list selection only changes highlighting. Old runs remain compatible, and the online path does not encode or save additional images.
- Added `just tum-post [seq] [runs...]` and `just tum-summarize [seq] [runs...]`: they post-process the newest or named `tum-run` result for a TUM sequence with object sentence embeddings and place/region clustering, while the latter also writes OpenAI region summaries. The existing CODa post-processing script now accepts a `RESULT_ROOT` override so both datasets share the same checked workflow without changing CODa's default output location.
- Added a design and phased TODO for lightweight internal pipeline monitoring: bounded non-blocking instrumentation, queue/worker/stage metrics persisted as JSONL, a loopback-only HTTP/SSE live view, and synchronized metric playback in the existing self-contained `replay.html`.
- Added the approved design, implementation plan, and root-level agent handoff TODO for a reusable 1 cm Open3D TSDF reference mesh in replay HTML, stable global label modes, and a high-contrast selected bounding-box overlay. The design keeps Hydra's dynamic mesh available, caches reconstructions per dataset, and explicitly distinguishes the RGB-D reconstruction from ground truth.
- Added `just orchestrator-graph`, a Python 3.8-compatible source analyzer, and a self-contained Argos-style code-reading guide for `PipelineOrchestrator.process_frame`. The generated page is now a pannable and zoomable processing canvas with deterministic call order, recursive expand/collapse, function search, breadcrumbs, and a right-side inspector. ### Changed

- `compose.yaml`: added the `daaam-ws` service (HTTPS git rewrite, git low-speed limits, model and pip caches kept in the workspace volume, `./datasets` mounted at `/datasets`); the existing `daaam` service is unchanged.
- `.gitignore` and `.dockerignore`: ignore `datasets/` and exported deployment bundles (`dist/`), and keep `logs`, `output` and `.claude` out of the Docker build context.
- `DOCKER.md` and `USAGE.md`: described the automated installation (`daaam-ws`, `docker/setup_workspace.sh`) and linked `DEPLOY.md`; `USAGE.md` also documents the live preview, including what to expect from it: the RViz window opens about 50 seconds before the first frame (pipeline initialization; about 26 seconds without the viewer), the red `Cannot register already existent type …` lines printed whenever `hydra_python` is imported (once per process) are harmless duplicate registrations, and the measured speed (the frame loop is sequential, CV then Hydra, and `--target-fps` is only an upper bound: about 3.4 frames/s without the viewer and 2.1 frames/s with RViz and ZMQ publishing; the GPU is busy only 30–40 % of the time).
- `scripts/run_tum_example.sh`: comment only; documents that `TARGET_FPS` is only an upper bound: the frame loop is sequential, so a target above the pipeline's own speed (about 3.4 fps without the viewer, 2.1 fps with it, on the reference machine and without DAM) changes nothing.
- `src/daaam/hydra/integration.py`: when the scene graph is published over ZMQ, the Hydra pipeline object is kept alive at shutdown instead of being destroyed. A run with a live viewer attached once segfaulted right after the results were saved, at the point where the pipeline and its ZMQ publisher were destroyed (the cause was not found: 1 crash in 8 runs); the process ends with `os._exit` in `scripts/run_pipeline.py` anyway.
- `scripts/run_tum_example.sh`: generated pseudo label files fall back to `/tmp` when the `config/` directory is read-only (a container started with another uid than the image's), and the run summary of `scripts/summarize_run.py` is printed when the pipeline finishes.
- `scripts/run_pipeline.py`: the process now leaves with `os._exit` (keeping the exit code) once `main()` has returned. After the grounding workers have been terminated, the feeder threads of the `multiprocessing` queues can block on a pipe nobody reads, which made the interpreter wait forever at exit although all outputs had been written. It also links `checkpoints/clip/ViT-B-16.pt` into `~/.cache/clip` before the pipeline starts, so that BoxMOT's CLIP-ReID loader no longer downloads the 335 MiB weights at every start (which fails or stalls without internet access and is lost with each `--rm` container). Likewise, when the DAM model is in the local Hugging Face cache, the DAM worker is pointed at the cached snapshot directory: the DAM loader otherwise queries the Hugging Face API for the repository id even though the weights are cached, which makes the DAM worker fail to start when offline. Delete the cached copy to update the model.
